# CLAUDE.md 整合规范（接入已有项目时）

接入一个已经有自己 `CLAUDE.md` 的项目时，怎么把框架约定和用户原有内容**整合成一份**文档。

> **为什么不能追加一段了事**：追加会留下两套口径并存——用户那半段说 A、框架这半段说 B，
> 模型读的时候不知道听谁的。**并存本身就是冲突没解决**。所以这里做的是整合，不是叠加。
>
> **为什么规范在 core 而不在 launcher**：合并规则与 `templates/claude-md-template.md` 死死绑在
> 一起——模板加一段、改一段，合并规则就必须知道有这么一段、该怎么处理冲突。同插件里放着，
> 一次改完；分开放就是新的漂移源，而且是「改了模板忘了改规则、下次接入才炸」的隐性漂移。

## 何时用

`project_scaffold.py` 对已存在的 `CLAUDE.md` **一律跳过不覆盖**。所以接入已有项目时，
框架约定不会自动进去——这份规范就是补那一步。

新建项目不适用：那时没有原文，scaffold 直接按模板渲染即可。

## 原则

1. **框架骨架为主**：产出文档用 `claude-md-template.md` 的章节骨架，用户内容填进对应位置。
   理由是接入之后整套协作都按框架的路径走，骨架必须是权威的那一套。
2. **用户内容一份不丢**：原文每一段都要有交代——保留 / 并入哪段 / 冲突已裁 / 建议删除+理由。
   **不允许静默丢弃**（对账纪律同 `requirement-archiving` 的全覆盖口径）。
3. **冲突要真解决**：同一主题只留一种说法，不并排堆两版。

## 第 1 步：分类原文

逐段读用户现有 `CLAUDE.md`，每段归入四类之一：

| 类型 | 判据 | 处理 |
|---|---|---|
| **业务内容** | 框架骨架里没有的东西：项目目标、业务背景、领域术语、技术栈约定、团队习惯 | **原样保留**，归入骨架对应段（多数进「项目目标」「业务背景」「项目特殊约束」） |
| **同主题·更具体** | 与框架同一主题，但写得比框架默认更细（例：他们的提测流程比框架的状态流转更具体） | **保留用户的**，放在框架段内作为项目级细化，并标一句「覆盖框架默认」 |
| **同主题·真冲突** | 与框架规定互斥，二者只能活一个（例：已有一套不同的任务状态名 / 与 modules/ 体系矛盾的目录约定） | **默认框架优先**，但必须在对照表里列出被覆盖的原文，让用户看见自己失去了什么 |
| **接入后失效** | 描述的东西接入后不再成立（例：指向即将被 modules/ 体系取代的目录结构） | 标出来 + 给理由，在对照表里问用户是删是改 |

判不准时**按「同主题·真冲突」处理**——宁可摆到用户面前，不要自作主张归成业务内容留着。

**「同主题·真冲突」的高频实例（2026-08-15 main-led 改造后新增）**：老项目的 CLAUDE.md 常写着
「主 Claude 不替代专职角色产出业务内容」「计划实施任务默认优先路由给 subagent」这类 role-led
硬约束——它们与现行框架的**自主判断**路由相反。按本表处理：框架优先，且必须在对照表里列出，
因为这条改动会**实打实改变主 Claude 的日常行为**，用户有权看见。

## 第 2 步：产出合并稿

按 `claude-md-template.md` 的章节顺序组织。三件事必须做到：

- **四个必备段一个不能少**：`## 角色体系`、`## 路由规则`、`## 任务状态流转与签发权限`、
  `## 文档与结构约定`（指向 `document-norms` skill）。它们是框架行为的契约，缺任何一个都会让
  对应机制静默失效——doctor 第 0 组的 `claude_md` 项就是查这四段。
- **四项 main-led 约定同样要带过去**。它们是「主 Claude 直做」这套模式的全部依据，漏了它照样会做，只是无据可依：

  | 约定 | 位置 | doctor 覆盖 |
  |---|---|---|
  | 主 Claude 直做纪律块（读契约与记忆 / skills 不自动触发 / 四类仍须委派 / 不得自签 QA） | `## 路由规则` 下 | ✅ token `agent-memory/` |
  | 代行段 | `## 任务状态流转与签发权限` 表后 | ✅ token `main-executed` + `签发权仍仅 @qa` |
  | 工种知识落点判据表 | `## 项目特殊约束` 下 | ✅ token `shared/notes.md` |
  | **scope 级指针**（auto-memory 每 scope 至多一行，不写条目级指针） | 写入纪律段内 | ❌ **无独立 token** |

  缺前三项 doctor 报 warn（非 error）；**第四项没有机器闸覆盖**——它通常与写入纪律同段，
  整合时连段带走即可，但别指望验收兜底。
- **占位符全部填实**：不留 `{{XXX}}`。值取自对话采集结果，与 scaffold 的 `--params` 同源。
- **用户原文的业务内容一字不改地搬**：不要顺手"润色"用户写的东西。

## 第 3 步：对照表（确认页必须展示）

```
原文去向对照（共 N 段）

| # | 原文段落 | 去向 | 说明 |
|---|---|---|---|
| 1 | ## 项目背景 | 保留 → 业务背景 | 原样 |
| 2 | ## 提测流程 | 保留（覆盖框架默认）→ 任务状态流转 | 比框架默认更具体 |
| 3 | ## 任务状态 | ⚠️ 已被框架口径取代 | 原文用 todo/doing/done，框架用 pending/in_progress/pending_qa/completed |
| 4 | ## 文档目录约定 | ⚠️ 接入后失效 | 与 modules/ 体系冲突，建议删除；保留会让 @pm 落盘路径歧义 |
```

**覆盖率必须 100%**：原文有几段，表里就有几行。判为删除的也要写理由。

## 第 4 步：备份与写入

**先备份再写**。是否需要额外备份文件，按两条确定性判断：

```bash
git ls-files --error-unmatch CLAUDE.md      # 被 git 跟踪了吗
git status --porcelain CLAUDE.md            # 输出为空才算干净
```

- 两条都通过（已跟踪 + 无未提交改动）→ **免备份**，git 里有原文，`git diff` 可看、`git checkout` 可回退
- 任一不通过（未跟踪 / 有未提交改动 / 不是 git 仓库）→ **必须**写一份
  `logs/CLAUDE.md.bak-<YYYYMMDD-HHmmss>` 再动手

> 为什么不无脑备份：项目里堆 `.bak` 文件是噪音，git 已经是更好的时间机器。
> 为什么不无脑靠 git：未跟踪的文件 git 里根本没有原文；有未提交改动时 `git checkout`
> 会把用户自己的活一起撤掉。这两个洞必须堵。

写入后在响应里告诉用户备份去了哪（或说明为什么没备份、怎么用 git 回退）。

## 反模式

- ❌ 追加一段「## Workframe 约定」了事——两套口径并存，冲突没解决
- ❌ 冲突项自己拍板不告诉用户——用户会在几周后才发现自己的约定没了
- ❌ 对照表只写"其余保留"——覆盖率不到 100% 的对账等于没对
- ❌ 顺手润色用户的业务描述——你不比他更懂他的业务
- ❌ 无条件覆盖原文件不留退路
