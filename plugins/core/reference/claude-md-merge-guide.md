# CLAUDE.md / AGENTS.md 整合规范（接入已有项目时）

接入一个已经有自己 `CLAUDE.md`（或 `AGENTS.md`）的项目时，怎么把用户原有内容和框架要求的结构**整合好**。整合产物是两个文件：

- **`AGENTS.md`**——项目自有的内容（这个项目是什么 / 项目自有判据 / 项目级角色 / 路由偏好 / 业务目录速查）＋ 委派授权，两扇门共用
- **`CLAUDE.md`**——头部信息、一行 `@AGENTS.md` 导入、订阅声明 / 快速入门 / 框架相关三段 CC 专属指路

框架自带的角色表、路由规则、任务状态流转与签发权限、两套记忆分工**不进这两个文件**：它们由会话启动时的注入片投递，随插件升级，项目侧没有副本可改——项目只能在 `AGENTS.md` 里**补充**，不能覆盖。

> **为什么不能追加一段了事**：追加会留下两套口径并存——用户那半段说 A、框架这半段说 B，
> 模型读的时候不知道听谁的。**并存本身就是冲突没解决**。所以这里做的是整合，不是叠加。
>
> **为什么规范在 core 而不在 launcher**：合并规则与 `templates/claude-md-template.md`、
> `templates/agents-md-template.md` 死死绑在一起——模板加一段、改一段，合并规则就必须知道有这么
> 一段、该怎么处理冲突。同插件里放着，一次改完；分开放就是新的漂移源，而且是「改了模板忘了改
> 规则、下次接入才炸」的隐性漂移。

## 何时用

`project_scaffold.py` 对已存在的 `CLAUDE.md`、`AGENTS.md` **一律跳过不覆盖**。所以接入已有项目时，
原文不会自动归位——这份规范就是补那一步。

**目标仓已经有自己的 `AGENTS.md` 时同样适用**（用别的编码 agent 的仓很常见）：用同一套四步流程
把它的原文分类、并进 `AGENTS.md` 的骨架（四个契约段 ＋ 项目段），不是在原文末尾追加几段。

**已装项目升级也适用**：上一版把项目目标 / 业务背景 / 项目特殊约束写在 `CLAUDE.md` 里，升级后会话启动（或迁移工具）
补建出来的 `AGENTS.md` 是占位骨架——「这个项目是什么」写着 `（待填）`，doctor 的 `agents_md` 项报 warn。这时的原文
是 `CLAUDE.md` 与 `.claude/rules/`（上一版同步进来的纪律镜像目录除外——就是 doctor 报「上一版的纪律镜像目录仍在」的那一个目录；`.claude/rules/` 下其余的 md 都算原文）：两扇门都要用的内容按下面的流程
归位进那副骨架，只对 CC 成立的可以留下。**别把 `CLAUDE.md` 整段复制过去**——那会把框架段落的旧副本与只对 CC
成立的内容一起带进 `AGENTS.md`。改 `AGENTS.md` 要用户本人确认，模型不代填。

新建项目不适用：那时没有原文，scaffold 直接按模板渲染即可。

## 原则

1. **框架骨架为主**：`AGENTS.md` 用 `agents-md-template.md` 的章节骨架、`CLAUDE.md` 用
   `claude-md-template.md` 的，用户内容填进对应位置。理由是接入之后整套协作都按框架的路径走，
   骨架必须是权威的那一套。
2. **用户内容一份不丢**：原文每一段都要有交代——保留 / 并入哪段 / 冲突已裁 / 建议删除+理由。
   **不允许静默丢弃**（对账纪律同 `requirement-archiving` 的全覆盖口径）。
3. **冲突要真解决**：同一主题只留一种说法，不并排堆两版。
4. **注入片投递的那几块不在项目文件里留副本**：原文写着的角色表 / 路由规则 / 状态流转 / 记忆分工，
   与注入片一致的判删除（对照表写明「由注入片投递」），项目自己的细化作为补充进 `AGENTS.md`，
   互斥的按真冲突处理。

## 第 1 步：分类原文

逐段读用户现有的 `CLAUDE.md`（目标仓有 `AGENTS.md` 的，连它一起读；已装项目升级时连 `.claude/rules/` 下项目自己的 md 一起读），每段归入四类之一：

| 类型 | 判据 | 处理 |
|---|---|---|
| **业务内容** | 框架骨架里没有的东西：项目目标、业务背景、领域术语、技术栈约定、团队习惯 | **原样保留**，归入 `AGENTS.md` 骨架对应段（多数进「这个项目是什么」「项目自有判据」「项目级角色」「业务目录速查」）；只对 CC 成立的内容可以留在 `CLAUDE.md` 导入行下面 |
| **同主题·更具体** | 与框架同一主题，但写得比框架默认更细（例：他们的提测流程比框架的状态流转更具体） | **保留用户的**，作为项目级**补充**写进 `AGENTS.md`「项目自有判据」，标一句「补充框架默认」。框架那几块由注入片投递、项目改不了，这里只能补充、不能覆盖；写成与注入片互斥的，就是下一行 |
| **同主题·真冲突** | 与框架规定互斥，二者只能活一个（例：已有一套不同的任务状态名 / 与 modules/ 体系矛盾的目录约定） | **默认框架优先**，但必须在对照表里列出被覆盖的原文，让用户看见自己失去了什么。框架那一侧由注入片每会话投递，项目文件里留着写反的说法只会让模型不知道听谁的 |
| **接入后失效** | 描述的东西接入后不再成立（例：指向即将被 modules/ 体系取代的目录结构） | 标出来 + 给理由，在对照表里问用户是删是改 |

判不准时**按「同主题·真冲突」处理**——宁可摆到用户面前，不要自作主张归成业务内容留着。

**「同主题·真冲突」的高频实例（2026-08-15 main-led 改造后新增）**：老项目的 CLAUDE.md 常写着
「主 Claude 不替代专职角色产出业务内容」「计划实施任务默认优先路由给 subagent」这类 role-led
硬约束——它们与现行框架的**自主判断**路由相反。按本表处理：框架优先，且必须在对照表里列出，
因为这条改动会**实打实改变主 Claude 的日常行为**，用户有权看见。

## 第 2 步：产出合并稿

两个文件各按自己模板的章节顺序组织。下面几件必须做到：

- **`CLAUDE.md` 里有一行有效的 `@AGENTS.md` 导入**：顶格写，不放进代码块、反引号或 HTML 注释。
  它是 CC 读到 `AGENTS.md` 的唯一入口——缺了它，`AGENTS.md` 在 CC 会话里一行都读不到，doctor
  第 0 组的 `claude_md` 项报 error。框架段落（角色表 / 路由规则 / 状态流转与签发权限 / 记忆分工 /
  文档约定）**不写进 `CLAUDE.md`**：写了 doctor 报 warn（与注入片形成双份）。
- **`AGENTS.md` 的四个契约段一个不能少**：`## 这个项目是什么`、`## 项目自有判据`、
  `## 委派子 agent`、`## 两扇门的差异`——doctor 第 0 组的 `agents_md` 项查这四段，其中委派段是
  另一扇门主动派子 agent 的显式授权。**正文不得出现 `@<file>` 导入**（有一扇门不展开它）。
  项目段（项目级角色 / 路由偏好 / 业务目录速查）照模板位置写；目标已有 `AGENTS.md` 时，把它的
  原文按第 1 步归进这副骨架，不另起一份。
- **占位符全部填实**：不留 `{{XXX}}`。值取自对话采集结果，与 scaffold 的 `--params` 同源
  （路由偏好段取 `role-profile-catalog.md` 里所选那一档的渲染文本）。
- **用户原文的业务内容一字不改地搬**：不要顺手"润色"用户写的东西。

## 第 3 步：对照表（确认页必须展示）

```
原文去向对照（共 N 段，两个文件合计）

| # | 原文段落 | 去向 | 说明 |
|---|---|---|---|
| 1 | ## 项目背景 | 保留 → AGENTS.md「这个项目是什么」 | 原样 |
| 2 | ## 提测流程 | 保留（补充框架默认）→ AGENTS.md「项目自有判据」 | 比框架默认更具体 |
| 3 | ## 任务状态 | ⚠️ 已被框架口径取代 | 原文用 todo/doing/done，框架用 pending/in_progress/pending_qa/completed（由注入片投递） |
| 4 | ## 角色分工 | 删除 → 由注入片投递 | 与框架角色表一致，留着与注入片形成双份 |
| 5 | ## 文档目录约定 | ⚠️ 接入后失效 | 与 modules/ 体系冲突，建议删除；保留会让 @pm 落盘路径歧义 |
```

**覆盖率必须 100%**：原文有几段，表里就有几行。判为删除的也要写理由。

## 第 4 步：备份与写入

**先备份再写**。两个文件逐个判是否需要额外备份，按两条确定性判断（以 `CLAUDE.md` 为例，
`AGENTS.md` 同理）：

```bash
git ls-files --error-unmatch CLAUDE.md      # 被 git 跟踪了吗
git status --porcelain CLAUDE.md            # 输出为空才算干净
```

- 两条都通过（已跟踪 + 无未提交改动）→ **免备份**，git 里有原文，`git diff` 可看、`git checkout` 可回退
- 任一不通过（未跟踪 / 有未提交改动 / 不是 git 仓库）→ **必须**写一份
  `logs/CLAUDE.md.bak-<YYYYMMDD-HHmmss>`（或 `logs/AGENTS.md.bak-<YYYYMMDD-HHmmss>`）再动手

> 为什么不无脑备份：项目里堆 `.bak` 文件是噪音，git 已经是更好的时间机器。
> 为什么不无脑靠 git：未跟踪的文件 git 里根本没有原文；有未提交改动时 `git checkout`
> 会把用户自己的活一起撤掉。这两个洞必须堵。

写入后在响应里告诉用户备份去了哪（或说明为什么没备份、怎么用 git 回退）。

## 反模式

- ❌ 追加一段「## Workframe 约定」了事——两套口径并存，冲突没解决
- ❌ 目标已有 `AGENTS.md` 时在它末尾追加四个契约段——同上，原文与骨架各说各的
- ❌ 把框架的角色表 / 流转表抄进 `CLAUDE.md` 或 `AGENTS.md`——注入片随插件升级、副本不会，两份一分叉模型按哪份做不可判
- ❌ 冲突项自己拍板不告诉用户——用户会在几周后才发现自己的约定没了
- ❌ 对照表只写"其余保留"——覆盖率不到 100% 的对账等于没对
- ❌ 顺手润色用户的业务描述——你不比他更懂他的业务
- ❌ 无条件覆盖原文件不留退路
