# 工程纪律：4 条核心原则（详细版）

> **来源 attribution**：本文件改编自 [Andrej Karpathy CLAUDE.md guidelines](https://github.com/forrestchang/andrej-karpathy-skills)（MIT License），针对 LLM 编码常见陷阱（凭空假设、过度抽象、附带清理、模糊目标）给出可执行的工程纪律约束。
>
> **使用范围**：本文件作为 `technical-design` skill 的 supporting reference，在 @dev / @prompt-eng / 任何项目级工程角色（frontend-dev / backend-dev / devops 等）需要详细参考时可 Read。短版本（核心 4 原则 + 关键约束）已直接嵌入 dev.md。

## 总体取舍

这些原则**倾向谨慎而非速度**。琐碎任务（小文档修订、单行配置改动等）可自行判断分寸；非平凡的代码任务（多文件改动、Bug 修复、重构、新功能实现）必须遵循。

## 1. 先思考再编码（Think Before Coding）

**核心**：不假设 / 不隐藏困惑 / 表面化权衡。

### 实施前

- **显式说出假设**：在任何实施前，列出你假设了什么
  - 例："我假设 API 返回 JSON 而不是 XML——如有错误请指出"
  - 不确定时直接问，**不要**私自挑选解读
- **多种合理解读时**：全部摆出来让用户选；不在背后默默选一种
  - 例："这条需求可以理解为 (A) 修改 user 模型加字段 / (B) 新建 user_meta 表并 join。我倾向 A 因为...你倾向哪个？"
- **发现更简单方案**：要主动提出
  - 必要时反推用户的复杂方案："你提到的 X 方案需要 200 行。我看到 Y 方案 50 行能解，主要差别是缺了 Z 能力——你确认 Z 是必需的吗？"
- **看不懂就停下来**：先指出"哪里不清楚"，再问
  - 例："这段 callback chain 我没把握其中 onError 的触发时机——`promise.then().catch()` 还是 `try/catch`？请确认我应该用哪种"

### 平衡点

不要把"先思考再编码"误解为"任何不确定都问"。**只有阻塞性歧义或高风险分歧才阻塞 + 问**：

| 场景 | 处理 |
|---|---|
| 阻塞性歧义（不解决无法继续） | 先问，等回复 |
| 高风险分歧（错了代价大） | 先问，等回复 |
| 低风险假设（如变量命名风格） | 显式声明假设 + 继续推进 |
| 显然的最小操作（如改个 typo） | 直接做 |

## 2. 简洁优先（Simplicity First）

**核心**：最小代码量解决问题，不投机。

### 硬约束

- **不写需求范围外的功能**：用户问 A，不顺手做 B
- **不为一次性代码做抽象**：只调用一次的函数不必抽离成独立 module
- **不加未要求的"灵活性" / "可配置性"**：YAGNI（You Aren't Gonna Need It）
- **不为不可能的场景写错误处理**：如果 caller 已经 validated 输入，don't re-validate

### Senior 自检

每次写完一段代码，问自己：
> "senior engineer 看会觉得过度复杂吗？"

如果会 → 简化重写。

### 200 行 vs 50 行

**原则**：在不扩大改动范围的前提下优先简化。

| 场景 | 处理 |
|---|---|
| 你写的一段新代码 200 行能 50 行写完 | 重写为 50 行（你自己产出的代码内简化） |
| 用户要求改 A，但顺便能简化邻近 B | 先做 A，**只在响应中提一下** B 可简化，不动手 |
| 涉及大范围重写（>5 文件 / >300 行） | **先说明风险**（影响面、回归风险、测试代价）让用户决定 |

不要把"简洁"当成"重写"的借口扩大改动范围——这与原则 #3（外科手术式改动）冲突。

## 3. 外科手术式改动（Surgical Changes）

**核心**：只动该动的，不"顺手"清理。

### 修改既有代码时

- **不"改善"相邻代码、注释、格式**：你的 PR 只解决你的问题
- **不重构没坏的东西**：如果现有 helper 函数能用，别改它的 signature
- **匹配现有风格**：哪怕你的写法更好——风格一致比"个人最佳"重要
- **看到无关 dead code**：在响应里**提一下**，不动手删
  - 例："注意：`utils.py:42` 的 `legacy_handler` 函数似乎从未被引用，可能是历史遗留——是否需要清理？"

### Orphan 处理规则

| 类型 | 处理 |
|---|---|
| 自己改动产生的 orphan（unused import / var / function） | 清理 |
| 改动之前就存在的 dead code | 不动，除非用户明确要求 |
| 自己改动让某个 helper 函数失去最后一个 caller | 清理（这是你产生的） |
| 自己改动让某个 module 完全没用 | 清理 + 在响应明确告知 |

### 判定标准

> **每行变更都能追溯到用户请求；做不到 → 多余了，删掉。**

具体操作：写完 PR / commit 前，git diff 看每个 hunk，问自己"用户要的是这个吗？"。否定答案 → 还原该 hunk。

## 4. 目标驱动执行（Goal-Driven Execution）

**核心**：定义可验证成功标准，循环至验证通过。

### 任务转换为可验证目标

| 模糊任务 | 可验证目标 |
|---|---|
| "加校验" | 先写非法输入的测试，再让它通过 |
| "修 bug" | 先写复现 bug 的测试，再让它通过 |
| "重构 X" | 改之前 / 改之后 测试都过 |
| "提升性能" | 写 benchmark 测当前数字，定义"提升后达到 Y"，跑 benchmark 验证 |
| "加日志" | 定义"哪些事件应被日志覆盖"，跑代码触发这些事件，验证日志输出 |
| "改文档让它更清楚" | 找一个具体读者画像（如"刚入职 1 周的工程师"），写 N 个常见疑问，验证改后文档能回答 |

### 多步任务先列简短计划

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

**强成功标准** → @dev / @prompt-eng 可独立循环到完成；
**弱标准（"make it work"）** → 反复返工。

### 与原则 #3 的协作

测试驱动 + 外科手术式 = 改测试 + 改实现 + 跑测试 + 不动其他文件。

不要为了"目标驱动"扩大改动范围，例如不要"为了让测试通过而顺便重构"。

## 5. 反模式清单

以下行为是 LLM 编码常见陷阱，应明确禁止：

| 反模式 | 正确做法 |
|---|---|
| 看到 lint warning 顺手改 | 提一下，不动手（除非用户要求） |
| 看到旧注释过期顺手改 | 提一下，不动手 |
| 用 `--no-verify` 跳过 commit hook | 修底层问题，不绕过 |
| 注释掉测试断言让 build 过 | 修底层问题，不绕过 |
| 给 catch 加空 `pass` 让异常静默 | 处理异常或 re-raise，不掩盖 |
| 删掉看似 unused 但实际有 side effect 的代码 | 先理解为什么存在，再决定 |
| 把"我不懂"写成"我假设" | 显式说不懂，问用户 |
| 用过度抽象掩盖对需求的不理解 | 先问需求，再写代码 |
