# PRD 通用写作纪律

> 本文件由 SKILL.md S3（填充）执行前读取，承载 core 层的**通用写作纪律**——与产品形态、
> 个人方法论无关的沉淀，core 持续迭代维护。**章节结构、各章写法、范式表、标注习惯不在
> 本文件**——那些属于项目层，见项目 `.claude/skills/prd-style/SKILL.md`（PRD 框架）。
>
> 分工与冲突：本文件的纪律默认适用于所有项目；与项目 PRD 框架冲突时**以项目为准**。
> 唯一例外是机器契约（frontmatter / 落盘路径 / 资产包结构 / AC 编号 / 变更留痕存在性，
> 清单见项目框架 §0）——任何一层都不覆盖它。

## 格式基线：纯 Markdown

PRD 全文使用通用 Markdown 语法（加粗 / 行内代码 / 引用块 / 围栏代码块 / GFM 表格；
表格单元格内换行用 `<br>`——这是**唯一允许的 HTML 标签**）。

`<text color>` / `<text underline>` / `<callout>` / `{folded="true"}` / `<sheet>` /
`<bitable>` 等平台专用扩展标签（飞书 lark-flavored 等）在本地与多数通用 Markdown
编辑器**无法解析**（原样显示为 HTML 文本、破坏阅读，已实证）——**默认一律禁用**；
仅当项目级 rule 显式声明启用且配备对应发布链路时才可使用，且发布前本地源文件仍保持
纯 Markdown、由发布 skill 做转换。

## 否定句裁剪

写「不做 / 不展示 / 不支持」前先判别：

| 类型 | 判别 | 处理 |
|------|------|------|
| **真边界** | 不写出来，开发大概率会做错（排除一个"自然而然的错误默认"） | 保留。全局性边界集中写在背景章「边界」小节；模块内局部反直觉规则就地写在对应表格行。每条全文只出现一次 |
| **过程残留** | 前面的肯定句已完备，否定只是记录"被否决过的设计提案" | 删除。它的归宿是「变更与决策记录」表，不是正文 |

示例：「重跑结果不入库、不覆盖原标签」是真边界（保留）；「结果区只展示重跑值，~~不展示
与原标签的对比~~」后半句是过程残留（删除，肯定句已完备）。

**决策表是唯一真相源**：正文不单设「本期不做 / Out of Scope」小节——做什么 / 不做什么 /
为什么，集中在「变更与决策记录」表与「边界」小节，不另开第三处。

## 变更融入三步（修订时强制）

正文永远是**当前真相的最优组织**，不是设计演进的考古层。需求补充 / 调整 / 变更时：

1. **定位**：按章节结构找到该内容的归属位置（哪个模块、哪张表的哪一行）
2. **融入**：在归属位置改写 / 增行，保持层级与类型有序
3. **记录**：在「变更与决策记录」表追加一行

**禁止**：为变更新开一个与已有模块平级的"补充点"章节尾插。确认过程标记一律不入正文——
包括"用户补充点 A"、"Q12 拍板"式来源标记，以及「（2026-06-11 拍板）」「（评审确认）」式
**日期/拍板标记**；结论直接作为需求事实陈述，拍板时间与背景只进「变更与决策记录」表。

## 段落组织（全文档强制：逻辑完整性 / 分类聚合 / 分点分段）

适用于**所有章节、所有模块**（含表格单元格内的文案说明）：

- **逻辑完整性**：同一主题的逻辑（含其全部分支/模式，如单次与批量、成功与失败）聚合在
  同一小节一次写完整，不按变更批次、新增时间切割到不同位置；小节开头用一句话交代该逻辑
  所属的功能模块/场景，不无上下文直接抛规则
- **分类聚合**：小节内需求点较多（≥4 条）时，用 2-6 字的分类小标题分组聚合（如「执行方式」
  「异常处理」「结果返回」「展示顺序」），类下放相关条目；不做无结构的长列表平铺
- **分点分段**：需求表达一律分点分段，一条只说一个意思；**非必要不用长句堆叠**——一句话里
  用分号串联 ≥2 条独立规则时，拆成多条
- **表格单元格**：单元格内含多条独立信息时，用 `<br>` 换行分点（或 ①②③ 编号），不用分号
  把多条规则挤成一长句；单条简短信息保持原样

## 精简表达（全章节适用）

用精简话语让读者一目了然，与段落组织并列的全文硬要求（用户多次实证纠正后固化）：

- **每点一句、30 字左右**：内容多时分点总结（必要时配分类小标题），不长篇罗列、不堆长句
- **括号补充每点至多 1 处**，宁可不加；口号式收尾（"满足 XX 核心诉求"类）删除
- **细节就位不前置**：链路构成、字段明细、内容块清单等只在归属章节写一次；概览 / 背景章
  不预写、不重复
- **护栏（优先于精简：精确 > 精简）**：精简只压表述，不得删减规则口径、判定条件、UI 逐字
  文案等规范性内容，不得让需求本意变形或变模糊——两者冲突时保精确，规则句/判定条件豁免
  「30 字」参考值；规范性分句宁可保留逐条结构也不合并压缩；AC、状态矩阵、接口口径以可验收
  为准，不为短而短。分级适用与 A 类补丁（表述精简 ≠ 内容取舍 / 删减红线 / 引用完整性等）
  见 skill: `document-norms` §11

## 安全项与校验口径的分级纪律

安全 / 合规 / 校验类内容按**产品生命周期阶段**给，不按「越全越好」堆：

- **demo 阶段走最小可用安全集**（≤8 项量级：配额 + 内容词库 + 格式 + 防抖）：不主动列
  PII / Prompt 注入 / 法律合规 / 越狱 / IP 限流，除非场景明确（已对接金融类客户 / 已上线 /
  已收到合规问询）
- **产品定位 ≠ 生命周期阶段**：海外定位 ≠ V1 强合规——GDPR / CCPA 是上线门槛不是 demo 门槛
- **完整调研可做但分级给**：主动给出「V1 最小集 vs 完整集」二选一让用户挑，不要逼用户砍
- **输入侧校验默认全 reject**：任何让需求载体不完整 / 不合规 / 不可处理的失败，统一走
  「reject + 友好提示 + 会话不杀」；PRD 开篇先声明这条统一路径再罗列各项
- **降级必须单独论证**：只有「降级产物对用户仍有明确价值」时才允许降级；同一类校验项不许
  一半阻断一半降级（防误点类防抖不属校验失败，是合理例外）

## 待确认项准入（严格）

只收录**用户明确提出**的未决事项——用户在需求沟通中明确表示"暂时不确定"、主动要求
"后续确认"的内容（含用户说"其余你看着填"时知情保留的 `[待确认]` 项）。

**禁止模型自行归档**：模型写作过程中产生的疑问、技术假设、风险提示**不得**写进待确认表——
这类疑问应在写作过程中**当场向用户提问确认清楚**（SKILL.md S3 的 `[待确认]` 占位 + 汇总
提问机制），确认结论直接融入正文；实现可行性类疑问留给研发评审环节，不由 PRD 替技术列出。

（待确认项的表结构与确认后处理见项目 PRD 框架对应章节。）

## 能力节：多维配置类交互设计

> **适用条件**：需求含 ≥3 维配置矩阵或多条件命中场景时启用本节；普通需求不适用。

- **≥3 维配置矩阵先定外层轴**：外层轴 = 业务方推理时最先想到的维度，不是工程上最干净的维度
- **维度间有语义耦合时不解耦展示**（如绑定的"内容-表达"对，不能拆成两条独立列表）
- **次要维度用卡片内横排 / 折叠 / 内嵌行承载，不用 Tab**——Tab 切断数据同步、引入跨 Tab
  漏配隐性 bug
- **组合数 ≥6 时必须主动提 fallback 设计**（默认值 / 跨条件复用），不等用户想起来
- **多条件命中场景必须有不可删、置底的默认条件**，避免配出「全不命中 = 无输出」的死路
- **缺失格子不藏**：直接显示 `→ 默认值` 等兜底文案，让业务一眼看出哪些是显式配置
