# 代码审查技能

## 产物去向

审查结论**默认只在响应中呈现**。用户要求存档时按 skill: `document-norms` §1 落
`projects/modules/<basic>/<sub>/requirements/<req_slug>/<sub_req_slug>/reviews/`；
发现的缺陷若需跟踪，走 `projects/issues/` + board task 草稿（不直接写 board）。

## 适用场景

- @dev 交付代码变更后
- @qa 做回归验证的前置检查
- 安全/质量疑点时的深度审查

## 四步流程

### 第 1 步：变更范围识别

读取代码变更（diff 或指定文件），识别：

| 维度 | 内容 |
|------|------|
| 改动文件 | 新增/修改/删除的文件清单 |
| 改动范围 | 每个文件的具体改动行数和函数 |
| 影响模块 | 直接调用改动代码的其他模块 |
| 依赖变化 | 新增/移除的依赖关系 |

### 第 2 步：多维度审查

#### 2.1 需求符合度（Requirement Conformance）

**前提**：先拿到规范资产（PRD 正文 / AC / spec / 词表 / 接口约定），**逐条比对，不能只看 AC** —— AC 是抽样，正文才是全量口径。

| 审查点 | 检查内容 |
|--------|---------|
| 规则落地 | 规范正文写明的每条规则，代码是否实现且口径一致 |
| 缺漏 | 规范写了、代码没做（含只做了一半、静默降级、开关/埋点等非功能要求） |
| 超纲 | 代码做了、规范没写（自行发挥的逻辑，需回溯确认） |
| 规范空白 | 规范本身没定，代码"忠实实现了不完整的规则" —— **不算实现错误**，退回需求侧补口径 |
| 已符合项 | 明确列出实现正确的部分，供修其他问题时防误伤 |

> 「规范空白」与「缺漏」必须分开报：前者要 PM/需求方先拍板，研发改了也是白改；后者研发直接修。

#### 2.2 正确性（Correctness）

| 审查点 | 检查内容 |
|--------|---------|
| 逻辑正确 | 代码实现是否符合需求/AC |
| 边界处理 | 空值、零值、极值、负数等边界条件 |
| 错误处理 | 异常捕获、错误返回、失败恢复 |
| 并发安全 | 竞态条件、死锁、共享状态 |
| 类型安全 | 类型断言、null 检查 |

#### 2.3 安全性（Security）

| 审查点 | 检查内容 |
|--------|---------|
| 注入风险 | SQL 注入、命令注入、XSS |
| 权限校验 | 未登录访问、越权访问 |
| 敏感信息 | 密码/密钥泄露、日志打印敏感数据 |
| 输入校验 | 未校验的用户输入、文件上传 |
| 依赖安全 | 已知漏洞的依赖库 |

#### 2.4 可维护性（Maintainability）

| 审查点 | 检查内容 |
|--------|---------|
| 命名清晰 | 变量、函数、类名能自解释 |
| 结构清晰 | 单一职责、合理抽象、避免过深嵌套 |
| 注释充分 | 复杂逻辑有解释，公开接口有文档 |
| 代码复用 | 避免重复代码，合理提取公共函数 |
| 测试覆盖 | 关键逻辑有测试 |

#### 2.5 性能（Performance）

| 审查点 | 检查内容 |
|--------|---------|
| 算法复杂度 | O(n²) 或更差的循环 |
| 数据库查询 | N+1 查询、缺失索引、全表扫描 |
| 网络请求 | 串行请求应并行、缺失缓存 |
| 内存使用 | 大对象加载、内存泄漏 |
| IO 操作 | 同步阻塞 IO、文件句柄泄漏 |

> **审查自己参与过的改动时**：一检（构建者正向）与二检（审计者反向）的完整判据见必载片 §验证纪律（必载，无需另找）。**二检换视角不能替代独立审查**——两者串联，本 skill 反模式末条说的就是这件事。

### 第 3 步：Finding 分级与归因

每个 Finding 打**三个正交标签**：风险级别（多急）+ 依据来源（凭什么）+ 处置方向（假绿还是假红，仅当被审对象自己在做判定时），再由这三者推出**第四个字段：是否触发新一轮**。

**风险级别**：

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| **Critical** | 必须修复 | 阻塞合并/发布，P0 问题 |
| **Warning** | 建议修复 | 下次迭代或同一 PR 修复 |
| **Info** | 建议改进 | 记录待办，不阻塞 |

**依据来源**（决定谁来处理、能不能拒绝）：

| 来源 | 含义 | 处理方 |
|------|------|--------|
| **违反规范** | 规范 / spec / PRD 明文写了，实现没做到 | 实现方直接修，无需再讨论口径 |
| **规范空白** | 规范本身没定，实现只是「忠实实现了不完整的规则」 | **需求方先补口径**，实现方此时改了也可能白改 |
| **审查者判断** | 无规范依据，属审查者的经验或偏好（架构选型、分层、工程实践） | **建议性质，实现方可拒绝**；单独分区，不与前两类混排 |

> 审查方通常看不到对方的发版流程、依赖约束、历史包袱，**架构决策权在实现方**。把「我认为这样更好」和「你违反了确认过的规范」混在一起报，会稀释真缺陷的紧迫感。

**处置轴**（被审对象本身在「判断别的东西对不对」时补打第三个标签）：

审查的是校验、断言、闸、评分标准、自查清单这类判定逻辑时，缺陷的**方向**比严重度更决定处置：

| 方向 | 是什么 | 处置 |
|---|---|---|
| **假绿** | 该拦的没拦住——条件写反、判定恒真、扫到 0 条也报通过 | **阻断**。它让所有依赖这道判定的结论一起失效，且失效时无声 |
| **假红** | 多拦了——把合法输入判成不合规 | **登记不阻断**。方向 fail-safe：它吵，但不会放过真问题 |

> 这一轴与风险级别**正交**，不是把三级细分成六级：一个 Info 级的假绿仍然阻断（它让一整片检查静默失效），一个看着吓人的假红只是噪声。**别用严重度替代方向判断**——假绿的严重度天生显得低，因为它什么都没报。

**第四字段 · 是否触发新一轮**（由前三个标签推出，不另判）：

| 条件 | 触发新一轮？ |
|---|---|
| 方向 ＝ **假绿** | **是**，无论级别多低——Info 级假绿同样阻断，理由见上一段 |
| 级别 ＝ **Critical** | 是 |
| 来源 ＝ **审查者判断** 且非假绿 | **否**——该来源已定为「建议性质，实现方可拒绝」，让它触发新一轮等于把可拒绝的建议变成强制项 |
| Warning／Info 且方向 ＝ 假红 | 否，登记后随下一轮一并核 |
| 打了 `(if-minor)` 标签 | **由打标签方判，不由修复方自判**，见下 |

> **`(if-minor)` 的兑现判定人写死为打标签方。** 它的意思是「如果这处确实琐碎就顺手改掉」，而**「是否琐碎」由打标签的审查方判定**。交给修复方自判会形成一个闭环：审查方打 if-minor → 修复方自己动手改 → 修复方判自己的改动琐碎 → 自己放行。整条链上没有第二个视角，而这正是 if-minor 这个标签当初想留住的东西。**修复方能做的是给出判断依据，不是做出判断。**

> **本步的产出会被签发档判定消费**：还有未兑现的假绿类 Finding 时，本轮不具备「有覆盖本轮 delta 的独立结论」这个前提（那份独立结论正在说它没过），签发档停在默认的完整验证。判据见必载片 §谁签发这次收口。

### 第 4 步：审查结论

```markdown
## 代码审查报告：{Task-ID / PR-ID}

### 审查范围
- 改动文件：{N} 个
- 改动行数：+{N} / -{N}
- 审查维度：需求符合度 / 正确性 / 安全性 / 可维护性 / 性能
- 比对的规范资产：{PRD / spec / 词表 / 接口约定，列出文件与版本}

### 已确认符合的部分（修其他问题时勿破坏）
- {规范条目} — {实现位置}

### Finding 列表（依据来源 = 违反规范）

#### 🔴 Critical ({N})
- **F-001**: {描述} — `文件:行号`
  - 依据：{PRD §X / spec 明文 / 团队规范}
  - 问题：{具体问题}
  - 建议：{修复建议}

#### 🟡 Warning ({N})
- **F-002**: {描述} — `文件:行号`
  - 依据 / 问题 / 建议：{...}

#### 🔵 Info ({N})
- **F-003**: {描述} — `文件:行号`

### 需求方待定（依据来源 = 规范空白，{N}）

- **N-001**: {描述} — 规范未定；当前实现 {现状}；备选 {a} / {b}，需 {需求方} 拍板后再排期

### 审查者建议（依据来源 = 审查者判断，可拒绝，{N}）

- **S-001**: {描述} — 无规范依据，属工程偏好，最终方案由实现方按自身约束判断

### 审查结论

- ✅ **通过** — 无 Critical，Warning ≤2
- ⚠️ **有条件通过** — 无 Critical，但有 Warning 需后续修复
- ❌ **不通过** — 有 Critical，必须修复后重新审查
```

## 与其他技能的协作

- **test-case-design**：代码审查与测试用例设计互补，审查静态、测试动态
- **systematic-debugging**：发现 Critical 问题时转为 Bug 追踪流程
- **technical-design**：如果审查发现方案设计缺陷，退回给 @dev 重新设计

## 审查优先级（时间有限时）

1. **必查**：Critical 级别的安全问题和正确性问题
2. **重点查**：修改密集区、历史 Bug 高发区
3. **快速扫**：简单的文本修改、配置变更

## 大范围审查的组织方式

单个变更走上面四步即可。**多文件 / 全仓 / 发版前**的成批审查另加一张透镜清单与三道工序，混合执行。

**八类排查透镜。** 本表只管**去哪找**；找到之后怎么定级与处置走第 3 步的三个标签——尤其处置轴（假绿阻断 / 假红登记不阻断）。

| # | 透镜 | 找什么 |
|---|---|---|
| L1 | 假绿灯 | `if not exists: continue` 型静默降级、扫 0 条报 ok、豁免过宽、多环链路断环不报错 |
| L2 | 双事实源漂移 | 硬编码数字（条目数 / 检查数 / 步骤数）、同一规则两处各写一份（**怎么处理**见必载片 §同一事实的多个表现层）|
| L3 | 退役概念残留 | 已删功能的名字仍留在文档里；重点在深层目录与模板正文——**越少被打开的文件，残留活得越久** |
| L4 | 死引用断链 | 改名文件的旧引用、不存在的路径 / 命令名 / wikilink（查漏 SOP 见 skill `document-norms` §8.3；项目用 obsidian 的走 skill `obsidian-link-audit`）|
| L5 | 流程自洽 | 步骤编号、段间引用、前后矛盾——尤其经历过多轮增改的文件 |
| L6 | 对外视角 | 对外产出里的内部痕迹：本机路径 / 内部人名 / 内部编号 / 私有仓引用；以及**陌生人拿着它照做一遍会卡在哪**。泄漏面的**具体红线清单由项目自己定义**，本 skill 不预设 |
| L7 | 契约-验证覆盖缝 | 文档声明的契约没有对应检查；新检查欠二检（二检口径见必载片 §新增检查必须用它自己的失败方式打一遍）|
| L8 | 墓碑内容 | 说的是真事、但话本身已无实质作用的历史残留。**三分判定**：①仍服务真实在场消费者的兼容逻辑 → 保留；②无在场消费者的纯历史叙述 → 清理，有存档价值的迁入档案；③拿不准 → 登记待裁（该写不该写的规则在必载片 §收口时的归位）|

**L3 与 L8 的边界**：L3 抓「指向已不存在事物的引用」（引用即是错）；L8 抓「所言为真但话本身无作用」。

**三道工序：**

| 工序 | 谁做 | 产出与约束 |
|---|---|---|
| **机器扫描先行** | 脚本，开审前一次性 | 词表扫全仓产出候选清单；误报由人裁，不由脚本裁 |
| **主会话深读** | 不委派 | 依赖全程上下文的单元（L5 流程自洽 / L6 对外视角 / L1 假绿灯）委派出去就断了上下文 |
| **subagent 批扫** | 委派，指令里写死**上表的透镜清单**与登记格式 | 机械透镜为主；**subagent 只报不裁，裁决权在主会话** |

**执行顺序**：先问清用户的前置问题 → 机器扫描 → 逐单元**只记账不动手** → 统一裁决三档（阻塞发布 / 本版修 / 下版修）→ 批量修复（每项动手前单独确认实现方式，修完做双检）→ 端到端走查。

> **中间那步为什么只记账不动手**：边审边修会不断改变被审对象，后面的审查失去稳定基线，最后那次绿也说不清是哪一版的绿。一行级的小修可以例外。

## 用外部工具或另一个模型交叉审查时

**发现值得看，上线判断不可信。** 实测两份外部报告：一份「暂不建议上线」的定级系统性偏高，另一份「可以上线」却把必现故障定成低优先级——最严重的那一条两份都没说准。**拿它们的 Finding，别拿它们的结论。**

**必须做一对一映射**：每条原始发现都要有落点——修了（附提交）/ 判定不修（附理由）/ 驳回（附证据）。

> **反面**：用「边读边归类」整合两份报告，34 条里 11 条从未进入任何编号，而整合报告写着「全部处理完毕」。归类是压缩动作，天然会吞掉不好归的那几条——**先逐条编号建账，再归类**。

## 反模式

- ❌ 只看代码不看上下文（没读 spec 就审查实现）
- ❌ 只对着 AC 审，不逐条比对规范正文（AC 是抽样，正文才是全量口径）
- ❌ **以审查者的架构偏好冒充缺陷**（无规范依据的建议混进 Finding 列表，稀释真缺陷）
- ❌ 把「规范空白」当实现错误报给实现方（应退回需求方补口径）
- ❌ 审的是判定逻辑，却只按严重度排序，不看假绿 / 假红方向
- ❌ 外部报告边读边归类，不逐条建账——归类会吞掉不好归的那几条
- ❌ 纠结风格问题，忽视安全和正确性
- ❌ 只说"这里有问题"，不说"应该怎么改"
- ❌ 对 Info 级别吹毛求疵，浪费时间
- ❌ 用 @dev 的自测结果代替独立审查
