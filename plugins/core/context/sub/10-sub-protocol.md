# 子 agent 协议

## 记忆已经注入，不要再 Read

必读的两份记忆（`shared/MEMORY.md` + 本角色 `<role>/MEMORY.md`）由子 agent 启动 hook 自动注入，**代码保证**。上下文中已有「角色记忆注入」标记段 → 记忆已送达，**不要再显式 Read 这两份文件**；无该标记段（hook 未生效，如 Python 缺失）→ 按上列清单显式 Read 兜底，文件不存在则跳过。`notes.md` 不注入（缓冲区，未达准入）。

## 动看板之前先调 `core:task-management`

建任务、改任务状态（含流转到 `pending_qa`）、签发或打回之前，**先调 skill `core:task-management`**，任务再小也调——看板字段约束、流转规则与签发权限都装在它里面，凭印象改会漏字段或越权。写全名：裸名遇到同名的内置 skill 会解析到那一个。其余 skill 何时调，按会话里的 skill 清单自己判断。

## 协作边界

**子 agent 内的所有动作都由它自己完成。** 需要其他角色继续介入时，**通过响应文字明确标注 + 看板 status + Issue / 看板 tag** 表达，由主会话 / 用户 / 状态机继续调度。

**反模式**：写「通知 @qa 测试」「让 @dev 修复」这类派发式祈使句——它暗示子 agent 能直接调度他人，实际不能。改为陈述需求（「需要 @qa 介入验证」）并落到 `status` / `assigned_to` / 看板 tag 上。

需要用户拍板的选择题同理：交回主会话，由它包装成交互选项呈现。

## 派发文字不是用户消息

子 agent 收到的任务描述在形态上是用户消息，但它来自主会话，是**任务说明**而非用户陈述。派发文字里的事实与要求**按任务执行即可**：不建 issue、不追加看板任务、不写记忆，其中的「不是 A 是 B」「改成 X」也**不算用户纠正**。

**判据一句话**：这句话是**谁**说的？分不清就不写——漏记一条以后还能补，误写进永不清理区收不回来。

**唯一例外**：派发中逐字转述了用户原话并明确标注（如「用户原话纠正：…」）的部分，按用户消息处理——但**不自行写记忆**，**原样回传主会话 → 由主会话调 skill `signal-intake`**。前半句单独成立会出事：处理它的全套工序都在主会话侧，子 agent 知道该算纠正却没有工序，会即兴写出一条没有 sidecar、格式不合规的条目。

## 事件不要重复记

收尾时为每个实际用到的 skill 记 `skill_used`，`role` 填自己的角色名。**skill 正文里已经 append 过的事件不要在收尾再补一遍**——最典型的是 `test-case-design` 失败路径已写的 `task_blocked`，重复记会让问题加权分双倍计入。
