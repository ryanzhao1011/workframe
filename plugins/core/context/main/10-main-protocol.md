# 主会话协议

## 通用角色与路由

| 角色 | 核心能力 |
|------|---------|
| @pm | 需求分析、功能拆解、验收标准、竞品调研、PRD 创作 |
| @dev | 代码实施、技术方案、Bug 调试、部署 |
| @qa | 测试用例设计、代码审查、Issue 管理、任务验证签发 |
| @prompt-eng | Prompt 设计优化、AI 策略、实验评估 |

- 消息以 `@角色名` 开头 → 直接调度对应角色
- 未指定角色 → 按任务性质与预期效果**自行决定直做或委派**
- **子 agent 返回的结果必须完整呈现给用户**
- 角色契约在插件的 `agents/<role>.md`，项目侧角色放 `.claude/agents/`（同名也与 core 并存，点名派谁用谁）；角色记忆在角色记忆目录下的 `<scope>/`（`<scope>` = 角色名或 `shared`；该目录是 `.workframe/agent-memory/`）
- 项目级角色与路由偏好写在项目根 `AGENTS.md`：只能**补充**本段，不能覆盖它

## 派发子 agent

**缺省主会话自己做完整条链路**（方案、实现、跑闸、文档同步、记账）。用户未点名角色时，只在四种情形派子 agent：**独立验证 ／ 权限隔离 ／ 可独立并行的大块 ／ 大量探索而只要结论**。「跨领域」「某角色更懂」不构成派发理由；把实现与测试拆给两方、按角色切分工作也不派。

- **按所需上下文拆派**：一个子 agent 只做一件事，别让它做完接着做下一件——后半程每一轮都背着前半程读进来的全部上下文
- **派工单写变更要点＋出处**（文件路径＋章节或 grep 关键词），保留「以原文为准」，但不要求整份通读：写明让子 agent 用 grep 或带范围的 Read 按需取段。**独立验证派工例外**：只给需求原文与被验对象，不给实现方的推理、要点与评价；验证方可自读需求、diff、完整代码、契约与测试——限制的是带偏，不是证据。实现方自报的未验项可以给，只当待验清单
- **独立验证的轮次由模型自评**（判据见必载片 §谁签发这次收口）：打回后实现方修，增量交独立方复核（增量动了前轮结论的前提就重查相关范围）；只修真实问题，不为防御性、措辞类问题返工；仍有关键问题 → 停止修补，重审方案或交用户——轮次上限不是收口理由。继承主对话上下文的派发形态（如 CC 的 fork）不独立，不得用于独立验证
- **CC 门：派发 `core:*` 角色不传 `name`**，续派用派发结果返回的 agentId 走 `SendMessage`。开着 agent teams 时带 `name` 的派发会以队友形态启动：`agent_type` 变成那个名字、角色记忆投不到，角色定义也可能不生效。PreToolUse hook 会拦下这种派发
- **Codex 门：派发角色时显式设 `fork_turns="none"`**，并在派工单写明必要上下文；默认继承父对话会被识别为 fork，跳过子 agent 纪律与角色记忆注入。需要继承父上下文时才使用 fork，并沿用父线程的纪律。

## 主会话怎么拿到角色记忆

子 agent 启动时的记忆注入不为主会话触发；两扇门都由 hook 投递：开场投 `shared/MEMORY.md` 全文与各角色条目目录；进入某域 skill（CC 门：调 Skill 工具或用户输入 `/skill`；Codex 门：读该 skill 的 `SKILL.md` 或用户在提示里写 `$skill`）、首次改到模块 `code_paths` 文件（只投 dev）时投该域 `<role>/MEMORY.md` 全文，每压缩周期每域一次，压缩后补投。

- 投递段标「未完整加载」→ 按其中路径 Read
- 只读分析、不进 skill 也不改文件时**不触发**——条目目录里有相关条目就自己去读全文，否则拿不到该域已沉淀的踩坑与用户偏好
- 直做某角色的活，先读一遍它的契约（工程纪律／产物合同／状态流转；路径见投递段或 §通用角色与路由）。**读 agent 文件 ≠ 获得 subagent 运行语义**：子 agent 必载片主会话收不到，要调什么 skill 自己按任务判断；动看板（建任务、改状态、流转、签发）之前照样先调 `core:task-management`
- **模块记忆不属于角色记忆**：基础模块或子模块存在 `module-memory.md` 且本线程碰到该模块时，hook 在工具调用后投递作业提醒；主线程每压缩周期一次，压缩后再次碰到才重投，子线程压缩后暂不恢复。shell 只识别模块文档路径；文件工具与 `apply_patch` 还查 `code_paths`。要提前了解就读对应模块的 `module-memory.md`。

直做实质性工作照走收尾三步，事件的 `role` 填 `main`——不记账的话，skill 使用率与问题信号只反映委派出去的那部分，自迭代的判断依据随之失真。

## 一条消息触发多条纪律时的处理顺序

**两层分开记，不混用去重逻辑**：消息事实处理（纠正识别 → 信号入账，记的是「用户说了什么」）与本轮工作收尾（`skill_used` 与 `task_blocked` fallback，记的是「我做了什么」）。同一事实同时满足两层时**只记一次**，按更早的那层记；skill 正文里已 append 的事件属于该 skill，收尾不再补。直做时这些步骤全在同一轮内完成，「刚刚已经写过一条」尤其容易再写一遍。逐步位序表见 skill `core:signal-intake` §9。

## auto-memory（CC 门）

- **写入纪律**（叠加在官方记忆指令之上）：单条 ≤3000 字符；**指针优先**——权威文档能推出的内容不复制进记忆，只存文档推不出的判断（环境坑 / 未决项 / 拍板理由）；**工作纪实**进 changelog / 文档，不进记忆；超预算 → 先落文档再指回，不硬塞不硬砍；**scope 级指针** = 工种知识迁往 `.workframe/agent-memory/<scope>/` 后，auto-memory 每 scope 至多保留一行权威指针（如「dev 域执行经验权威见 `.workframe/agent-memory/dev/MEMORY.md`」），**不写条目级指针**。
- **清理判据**（模型只提候选，归档/删除一律用户拍板）：需求完结后其记忆压成一行指针；同模块 ≥3 条记忆合并为一条（**scope 级指针行豁免**）；已完结且文档承载的工作记忆 → 归档 = 文件移入 `.workframe/memory-archive/` + 删索引行（**文件不灭：git 可溯 + 仓库外备份**）。
