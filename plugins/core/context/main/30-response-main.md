# 响应输出（主会话）

## 选择题式澄清必须用 AskUserQuestion

**硬约束**：向用户抛出**选择题式澄清问题**（已有候选选项 A/B/C 让用户挑）时，**必须优先调用 `AskUserQuestion`** 渲染交互选项卡，而不是在纯文本消息里列 A/B/C 让用户手敲回复。

- **适用**：需求范围二选一 / 多选一、技术方案候选比较、验收标准粒度选择、优先级裁决、命名风格选择
- **不适用**（仍用自然语句提问）：开放式问题；需要用户填具体数值 / 名称 / 描述的问题
- **复杂内容确认（硬约束）**：被确认对象是表格 / 多行示例 / 代码块 / 结构预览等复杂内容时，必须**先在响应正文中独立完整展示**，选项只做轻量判断（「符合，按此执行 / 需调整」）；**option preview 不承载关键信息**——部分客户端对 preview 渲染不全，会导致确认空转
- **工具加载**：该工具在部分会话中以 deferred tool 形式出现，报 schema 未加载时先用 `ToolSearch` 以 `select:AskUserQuestion` 加载再调用
- **无该工具的受限环境**：退化为自然语言澄清——正文中编号列出 A/B/C + 推荐项 + 简短理由，请用户回复编号。不因工具不可用而拒绝继续

**转述 subagent 的问题时同样遵守**：subagent 返回的内容里若含选择题式澄清（纯文本 A/B/C 列表），**必须用 `AskUserQuestion` 重新包装**后再呈现，不能把纯文本选项原样贴出。

## 确认信号识别

完成输出后等用户确认，再执行文件写入。**关键边界**：用户回应是「补充事实/参数」还是「否定方向 / 改写结构 / 要求重做」，决定是否需要二次确认。

**视为确认（可直接合并并写入）**：

- 明确批准词：确认、好的、可以、没问题、写吧、y、yes、行、方案 ok
- **补充事实 / 补充参数**：提供新的具体数据点、字段、参数、示例数据，**且未否定当前草稿的整体方向和结构**（例：「优先级改 P1 而不是 P2」「再加上权限校验字段」「这个表名叫 user_session 不是 sess」）

**不视为确认（必须重新展示 + 二次确认）**：

- 用户发出与当前草稿无关的新任务指令（暂存当前草稿，执行新任务）
- 用户**否定当前方向 / 要求改写结构 / 要求重做**（例：「这个思路不对，换一种」「重新写一版」「AC 重新拆」「整段重写」）→ 先修改，重新展示完整草稿，再等二次确认
- **歧义情况**（介于「补充」和「改写」之间）：默认走二次确认，宁多一轮不少一轮

判断口径：补充 = 在不动骨架的前提下加细节；改写 = 改骨架/方向。前者直接合并，后者必须二次确认。
