# 信号入账（主会话）

用户消息里的**新事实与指令**要落进项目资产，用户的**纠正**要落进记忆高置信区。本段管**判据**：什么触发、算哪一档、落哪个点；工序（怎么写、写成什么格式）在对应 skill 里。

## 什么不触发

**判断标准**：用户是在**陈述新事实或下达指令**（触发），还是在提问咨询 / 假设讨论 / 转述他人未确认采纳的说法 / 回顾已有事实（**均不触发**）？歧义时先向用户澄清。

纠正信号另有一条排除：纠正的对象必须是**持久层认知**（跨轮次、跨需求仍成立的事实 / 口径 / 工作方式 / 偏好）。**对当前草稿的一次性修改意见不算**——改标题、换措辞、调本篇结构、本方案内的取舍，按「补充 vs 改写」判定直接修改产出即可，不写记忆、不发 `user_correction` 事件。

- **判据一句话**：这句话在下一个不相关的任务里还成立吗？成立 → 纠正；只对当前这份产出成立 → 修改意见
- **歧义裁决**：含「以后 / 都 / 每次 / 记住」等持久化信号词 → 按纠正处理；没有 → 按修改意见处理。同一修改意见被用户再次重申时命中「重复强调」信号，升级为纠正

## 纠正的检测信号

**否定**（不是 / 不对 / 错了 / 不应该）／**修正**（应该是 / 改成 / 用 X 而不是 Y）／**重复强调**（我说过 / 之前告诉你 / 记住 / 注意）——最后一类尤其要接住：它意味着同一事实此前已纠正过至少一次而未被记住。

命中后：先回显「收到纠正：[错误认知] → [正确信息]。已记录。」，再按下面的分流写入。

## 优先级

| 级别 | 含义 | 确认要求 |
|---|---|---|
| **P0** | 错误代价高：系统安全 / 重大泄露 / 线上故障，或产品方向性变更（需求范围 / 优先级 / 上线时间） | **先回显摘要、等用户确认，再写入**。顺序不可颠倒，不允许先写后确认 |
| **P1** | 影响产品方向或技术架构，但无即时风险 | 回显摘要后可直接写 `notes.md` / 角色级 `MEMORY.md`；看板任务一律走 `task-management` skill 或主会话落盘；触及受保护资产须用户确认并交由 owner 角色执行 |
| **P2** | 有参考价值，不影响当前迭代 | 即时归档，无需确认 |

## 触发类别与落点

| 档 | 类别 | 落点 |
|---|---|---|
| P0 | 安全问题 / Prompt 泄露风险 | `projects/issues/SEC-{序号}.yaml`（泄露类 title 前缀 `[Prompt泄露]`）+ 看板追加 P0 任务（`assigned_to: dev`，`tags` 含 `needs-qa-regression`）|
| P0 | 需求变更（含范围 / 优先级 / 上线时间调整） | **响应中输出 PRD 草稿 + 看板 task 草稿**，不直接写文件；PRD 由 @pm 落盘、task 由主会话落盘 |
| P0 | 线上故障 | `projects/issues/BUG-{序号}.yaml` + 看板 P0 任务（`assigned_to: dev`）|
| P1 | 技术决策（架构选型 / 数据库 / API 设计 / 依赖选择） | **决策本身落文档**（单模块进该子模块 `decisions/`，跨模块进 `projects/specs/plans/`），`@dev MEMORY.md` **只留一行指针**；只有纯执行经验（踩坑、工具用法、本机环境）才直接进 `@dev MEMORY.md` |
| P1 | Prompt 策略变更 | `@prompt-eng notes.md` + 高置信事实进其 `MEMORY.md`；响应中输出 `tags: [prompt-review]` 的 task 草稿。质量下降已影响用户 → 升 P0 |
| P1 | LLM 模型/成本（涨价 / 新模型 / API 变更 / 下线 / 降级链） | `@dev MEMORY.md` + 评估路由策略的 task 草稿。模型下线或破坏性变更 → 升 P0 |
| P1 | 质量标准调整（敏感词库 / 质量分权重等判定标准） | `@qa MEMORY.md` + `@prompt-eng MEMORY.md` |
| P1 | 工作方式 / 流程（「以后 XX 要这样做」、对产出的正负面评价） | 正负面反馈 → 对应角色 `notes.md`（D/U/R/A ≥2 则提升）；流程调整 → `shared/notes.md` + 流程调整建议；涉及角色 / 纪律 / skill 文件的修改走 `/core:self-iteration` 提案或用户显式审批，**不直接落盘** |
| P2 | 行业动态 / 通用参考信息 | `@pm notes.md` |

**需求变更 vs 线上故障**：系统按预期运行但输出不满足用户预期 → **需求变更**；系统未按预期运行 → **线上故障**。

**上表只装领域无关的通用触发。** 业务特定的触发词（客户线索、合规预警、社媒发布、功效宣称这类）由项目自己加，写进项目自有判据（`AGENTS.md`）或项目自己的 skill，并继承本段的排除判据、优先级分档与写入工序——**框架不替项目猜它的业务**。

## 纠正的落点分流（判据 = 谁消费）

> **直做时怎么对号入座**：下面四个分支的主语写的是「角色」，但判据从来是**谁消费**、不是谁挨的批评。主会话直做 dev 域的活被纠正了一个工程习惯——消费者是未来做该域活的人（含 @dev subagent），走第三分支落 `dev/MEMORY.md`。拿不准时问一句：*换成 @dev 被派去做同一件事，它需要知道这条吗？* 需要 → 角色域。

| 分支 | 落点 |
|---|---|
| 业务事实 / 需求口径（消费者是查该模块的人） | 正确信息落对应模块文档为权威；MEMORY 高置信区只写一行指针条目 |
| 主会话协作行为（配合方式 / 输出形态 / 工作流程） | 主会话侧的官方记忆机制（**两扇门各用各自的原生机制，不共享**）；不写 role/shared，**跳过 sidecar**，事件仍写（`scope` 填 `main`、省略 `entry_key`）|
| 角色执行 / 跨角色口径 | 对应 `<role>/MEMORY.md` 或 `shared/MEMORY.md` 高置信区 |
| 双消费（主会话和角色都要遵守） | `shared/MEMORY.md` 存全文为权威 + 主会话记忆只留一行指针，不复制全文 |

**判定要写入之后 → 调 skill `signal-intake`**：落盘那一步的全部工序（A.U.N. 写入前必做、Issue 模板与编号、执行规范八条、`[纠正]` 条目的写入格式、sidecar 字段与 `entry_key` 归一、supersede 的落盘动作）都在那里，本段只管判据。

**要写事件行 → 调 `workframe-event`**：纠正事件的机械写法同样走它，`scope` **必须填实际值**（角色名 / `shared` / `main`），把 `role`、`<role>` 这类占位符原样写进 sidecar 的条目谁都查不到、也无法参与容量与保护判断，等于白写。

## 纠正条目的三条原则

- **`[纠正]` 标记的内容永不清理**。指针化不算清理——业务事实类条目把正文移交权威文档、压缩为一行指针后，标记、日期与 sidecar 保护依然在位
- **`[纠正]` 条目必须有 sidecar 保护**：`protected=true`、`provenance=user-decree`、`source=[纠正]`
- 用户纠正具有最高权威性，优先级高于任何其他信息源；同一主题被多次纠正时保留最新，旧的移 `notes.md` 留档并同步删掉旧 sidecar 条目，**不直接删**

## 这条纠正是不是通用规则

评估该纠正是否具有通用性（不仅限于当前场景）：

- **具有通用性** → 这是**「用户显式确认」入口**，可创建 / 更新**项目自有的判据落点**（项目根的 `AGENTS.md`，或项目自己的 skill）。**必须先回显摘要并等用户明确确认才落盘**；用户未明确确认 → 不落盘，建议走 `/core:self-iteration` 提案审批作为更受控的入口
- **禁止目标**：框架自带的注入源与 skill——那些走自迭代提案路径，是另一个独立入口，与本条不冲突
- **仅限特定场景** → 只写记忆，不动项目判据落点

**要往项目判据落点里写一条纪律之前先问一次**：这条能不能变成**机器闸**（断言 / 校验 / hook）？能 → **优先落闸**——纪律要靠模型每次都记得住才生效，闸不用。落闸之后再决定还要不要配一段纪律文本、放哪一层（落点分层见 `librarian` skill）。

## 关联任务的粒度

P0 类紧急变更（安全 / 线上故障）在用户确认后，在看板 `tasks:` 末尾追加**单条** `status: pending` 任务（`tags: [auto-update, <类别>]`），**仅作为信号标记进入待处理队列**——下次会话由用户 / 主会话看到看板时分配处理，不自动派发。
