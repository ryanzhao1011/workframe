# 响应输出（通用）

## 响应消息优先于文件写入

执行分析 / 设计 / 审计 / 评估任务后按此顺序：

1. **先在响应消息中呈现完整内容**（结论、草稿、报告全文）
2. **等用户确认任务完成后再写入文件**（文档、策略文件等）
3. **收尾归档（日志、看板更新）最后执行**

**禁止**用「结果已写入 XXX 文件」代替实际内容输出。

## 执行过程中的自然澄清

遇到以下情况，**在继续执行前先提问**，不要假设：已提供的信息不足以支撑最佳产出；任务描述存在多种合理解读；发现与现有文档／规范有重要冲突；关键决策点有多个方向且影响后续较大。

提问方式：用自然语句，一次最多提 1-2 个关键问题，并给出几个建议选项；不要一次性批量罗列疑问清单。

## 陈述可证伪

报告做了什么时，说法必须能被对方验证或推翻：

- 写「已验证」必须说明**验的是哪几项、不含哪几项**——不写范围的「已验证」等于没说
- **「实现完成」≠「验证完成」**：只跑通了主路径就说「完成」，读者会按「全都测过」理解
- commit message 与任务状态说明里的陈述同样自查，它们比响应更长寿
- **「不含」也会写空转**——落笔前问：这条排除的是真实风险面，还是在本次改动范围内**恒真**的命题？恒真的读起来谨慎、信息量为零，还会挤掉真正该披露的那条

## 无需等待确认、直接执行的操作

以下为系统维护类操作，低风险，直接执行：看板 `status` 字段更新；`MEMORY.md` / `notes.md` 知识条目追加；看板 `summary:` 统计数字重算（由 hook 自动 + 会话启动漂移检查兜底；用户也可显式调 `workframe-recompute-board-summary`）。
