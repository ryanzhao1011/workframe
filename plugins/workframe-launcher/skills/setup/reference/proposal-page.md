# 方案确认页渲染规范

> `setup` skill §4 的展开。确认页是写盘与订阅前的**唯一闸门**，本质是把确认从
> 「审文件清单」升级为「审认知」——PM 确认的是「你们对我业务的分层理解对不对」，
> 而不是「这些文件名对不对」。

## 三条硬性标准

### 1. 用 PM 自己的业务语言展示模块树

**有存量资料时**：展示分析推荐的真实 basic / sub 树，每个节点用业务名，并标出证据来源
（哪些文件 / 哪段代码支撑这个切分）。

**无资料时**：按 Q1 采集的产品类型渲染一棵**示例树**，并明确标注：

> 这是按你的产品类型给的示例结构，真实模块之后用 `/core:module-init` 一个个长出来。

不允许只给空骨架就让用户确认——PM 无法对空结构做判断。

### 2. 「你以后每类东西放哪」映射表

必须给出**具体路径**，不能只说「按 modules 体系组织」。**完整表**至少覆盖：新需求 PRD、
测试用例、代码现状快照、上线复盘、跨模块技术方案、单模块决策记录、公司资料、个人产出——
内容以 `document-norms` §1 归属矩阵为准（唯一事实源）。**这张表只在确认页展示、不写进
CLAUDE.md**——2026-08-15 起 CLAUDE.md 模板只保留指向 `document-norms` 的指针，不内嵌副本：
副本一旦与 §1 分叉，读到副本的人就照错的做，而它会无条件进入每个新项目的必载上下文。

**确认页只展示其中最常用的几行**（挑用户业务里马上会用到的），末尾一句指明完整版去处——
这张表是教用户认识框架的，不是等用户拍板的，压缩不影响决策（2026-08-11 用户拍板）。

### 3. 框架术语必须带业务例子

首次出现的框架概念一律「术语 + 一句人话 + 用户自己业务的例子」。典型需要翻译的：

| 术语 | 说法 |
|---|---|
| basic 模块 | 一条产品线 / 一个大功能域，例如「<用户业务里的某条线>」 |
| sub 模块 | 该产品线下相对独立的一块，例如「<某个具体子系统>」 |
| 需求资产包 | 一个需求从 PRD 到测试用例、原型、复盘的一整套文件，放在同一个目录里 |
| current-state | 代码现状快照，由工具从真实代码反解生成，用来对账「文档说的」和「代码干的」 |

裸术语出现即视为不合格。

## 渲染约束（终端里读，不是网页里读）

确认页在**终端**里显示，不是 markdown 预览器：

- **禁止任何 HTML 标签**（`<br>` `<b>` `<code>` …）。终端会把它们原样吐出来。
- **一个单元格只放一件事**。想在格子里塞「路径模式 + 业务例子」两行内容，就是去用 `<br>` 的
  动机所在。要举例就**另起一行**，用 `例：` 开头列在表格下方。

> 实测（2026-08-10 走查 R3）：映射表为了在一格里同时放路径模式与业务例子用了 `<br>`，
> 终端里原样显示成 `prd.md<br>例：…`。表格本身的对齐与宽度实测**没有问题**——初版走查
> 曾据错乱的粘贴文本误判为「表格撑爆宽度」，看真实截图后撤回该结论。

## 页面结构

按此顺序渲染，全部在**正文**展示（不塞进 AskUserQuestion 的 option preview——部分客户端
渲染不全，已多次导致确认空转）。

**分档呈现**（2026-08-11 用户拍板：确认内容偏多核对费劲）：**决策档**——会写进或改动用户
文件的内容、用户可当场驳的推断——完整展示；**告知档**——纯介绍、日后随时可查的——压到
最短并指路。典型归属：1 / 2 / 5 / 7 与 8 中会动已有文件的项属决策档，3 / 4 属告知档，
其余按判据归。首次接触的框架概念在决策需要处照常讲人话，但只讲一次。压缩幅度按现场判断，
底线是**决策对象不因简洁缺席**。

1. **项目基本信息**：展示名 / 目标目录 / 一句话目标 / 业务背景摘要
   —— 后两项由 Q1 派生（见 SKILL §2「必填字段从哪来」），**必须在这里展示让用户过目**：
   它们会原样写进 CLAUDE.md，用户不看一眼就没人看了
2. **模块树**（标准 1）
3. **「东西放哪儿」映射表**（标准 2）
4. **自动获得的能力**：core 的 4 角色 + skills + rules + hook 链路，一句话带过即可，不逐条罗列
5. **角色路由偏好**：推断出的 role_profile + 主力/按需/几乎不用三栏 + 一句「不符合实际可当场改」
6. **存量资料批次概览**（仅 B 路径）：按资料形态给批次与去向概览；**单份文件的安置与
   原件处置不在本页拍**——建树后的逐模块小闸（SKILL §5 步骤 4）深读后逐模块确认、当场执行
7. **CLAUDE.md 整合结果**（仅 B 路径且目标已有 CLAUDE.md）：见下方专节
8. **将要执行的动作清单**：建目录 → 落骨架 →（B 路径）写合并后的 CLAUDE.md → 订阅 core →
   同步 rules → **git init + 首提交** → 落盘验收，让用户知道确认后会发生什么
   —— **`git init` 是可勾选项，默认勾上**。没有 git，`.gitignore` 就是废的、可移植性检查会
   整个跳过、「同事 clone 接入好的项目」这条路径也不成立。目标已经是 git 仓时这一项不出现。

## CLAUDE.md 整合结果（B 路径专节）

这是整个确认页里**唯一会改写用户既有文件**的一项，展示标准比其他项更严：

1. **合并稿按段落差异露出，不贴全文**（2026-08-11 定稿，取代早期「合并稿全文」要求，
   与 SKILL §3「只露含用户原文的段落」对齐）：**含用户原文的段落**逐段处理——原样保留的
   只列段名；被改写 / 被合并的给「原来是什么 → 现在是什么」对照；框架样板段（订阅声明 /
   角色体系 / 路由规则 / 状态流转，每个项目一模一样）一行带过。用户想通读时随时给全文
2. **原文去向对照表**——原文每一段都要有一行，覆盖率 100%。格式与判据见 core 的
   `reference/claude-md-merge-guide.md` §第 3 步
3. **被覆盖项单独点名**——冲突默认框架优先，但每一条被框架口径取代的原文都要在正文里
   显式列出（不能只埋在对照表里），并说清「原来是什么 → 现在是什么 → 为什么」
4. **备份去向**——按 git 跟踪与干净状态判定的结果，明确告诉用户原文在哪、怎么回退

用户对被覆盖项有异议时：改的是**合并稿**，不是回头改框架骨架。改完按下方 §确认交互 的局部重渲染规则再确认。

## 确认交互

用 AskUserQuestion，三个选项：

- `按此执行`
- `我要调整` —— 用户用自然语句说改什么，改完**重渲染受影响的 section**、声明一句
  「其余未动」再确认（2026-08-11 拍板，取代「重新完整渲染」：旧拍板防的是口头描述代替
  渲染，局部重渲染不违背其动机）；改动牵连多个 section、或用户否定的是整体方向时，
  仍完整重渲染。不做增量口头描述
- `取消`

判据：用户补充事实或参数（改个名字、加个模块、换 role_profile）→ 合并后可直接执行；
用户否定方向或要求重来（「模块这么分不对」「换个思路」）→ 必须重新渲染 + 二次确认。
歧义时走二次确认，宁多一轮不少一轮。
