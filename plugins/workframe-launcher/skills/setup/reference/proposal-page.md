# 方案确认页渲染规范

> `setup` skill §4 的展开。确认页是写盘与订阅前的**唯一闸门**，本质是把确认从
> 「审文件清单」升级为「审认知」——PM 确认的是「你们对我业务的分层理解对不对」，
> 而不是「这些文件名对不对」。

## 三条硬性标准

### 1. 用 PM 自己的业务语言展示模块树

**有存量资料时**：展示分析推荐的真实 basic / sub 树，每个节点用业务名，并标出证据来源
（哪些文件 / 哪段代码支撑这个切分）。

**无资料时**：按 Q1 采集的产品类型渲染一棵**示例树**，并明确标注：

> 这是按你的产品类型给的示例结构，真实模块之后用 `/core:module-init` 一个个长出来。

不允许只给空骨架就让用户确认——PM 无法对空结构做判断。

### 2. 「你以后每类东西放哪」映射表

必须给出**具体路径**，不能只说「按 modules 体系组织」。**完整表**至少覆盖：新需求 PRD、
测试用例、代码现状快照、上线复盘、跨模块技术方案、单模块决策记录、公司资料、个人产出——
内容以 `document-norms` §1 归属矩阵为准（唯一事实源）。**这张表只在确认页展示、不写进
CLAUDE.md / AGENTS.md**——指向 `document-norms` 的触发指针在必载注入片里，项目文件不内嵌副本：
副本一旦与 §1 分叉，读到副本的人就照错的做，而它会无条件进入每个新项目的必载上下文。

**确认页只展示其中最常用的几行**（挑用户业务里马上会用到的），末尾一句指明完整版去处——
这张表是教用户认识框架的，不是等用户拍板的，压缩不影响决策（2026-08-11 用户拍板）。

### 3. 框架术语必须带业务例子

首次出现的框架概念一律「术语 + 一句人话 + 用户自己业务的例子」。典型需要翻译的：

| 术语 | 说法 |
|---|---|
| basic 模块 | 一条产品线 / 一个大功能域，例如「<用户业务里的某条线>」 |
| sub 模块 | 该产品线下相对独立的一块，例如「<某个具体子系统>」 |
| 需求资产包 | 一个需求从 PRD 到测试用例、原型、复盘的一整套文件，放在同一个目录里 |
| current-state | 代码现状快照，由工具从真实代码反解生成，用来对账「文档说的」和「代码干的」 |

裸术语出现即视为不合格。

## 渲染约束（终端里读，不是网页里读）

确认页在**终端**里显示，不是 markdown 预览器：

- **禁止任何 HTML 标签**（`<br>` `<b>` `<code>` …）。终端会把它们原样吐出来。
- **一个单元格只放一件事**。想在格子里塞「路径模式 + 业务例子」两行内容，就是去用 `<br>` 的
  动机所在。要举例就**另起一行**，用 `例：` 开头列在表格下方。

> 实测（2026-08-10 走查 R3）：映射表为了在一格里同时放路径模式与业务例子用了 `<br>`，
> 终端里原样显示成 `prd.md<br>例：…`。表格本身的对齐与宽度实测**没有问题**——初版走查
> 曾据错乱的粘贴文本误判为「表格撑爆宽度」，看真实截图后撤回该结论。

## 页面结构

按此顺序渲染，全部在**正文**展示（不塞进 AskUserQuestion 的 option preview——部分客户端
渲染不全，已多次导致确认空转）。

**分档呈现**（2026-08-11 用户拍板：确认内容偏多核对费劲）：**决策档**——会写进或改动用户
文件的内容、用户可当场驳的推断——完整展示；**告知档**——纯介绍、日后随时可查的——压到
最短并指路。典型归属：1 / 2 / 5 / 7 与 8 中会动已有文件的项属决策档，3 / 4 属告知档，
其余按判据归。首次接触的框架概念在决策需要处照常讲人话，但只讲一次。压缩幅度按现场判断，
底线是**决策对象不因简洁缺席**。

1. **项目基本信息**：展示名 / 目标目录 / 一句话目标 / 业务背景摘要
   —— 后两项由 Q1 派生（见 SKILL §2「必填字段从哪来」），**必须在这里展示让用户过目**：
   它们会原样写进 AGENTS.md，用户不看一眼就没人看了
2. **模块树**（标准 1）
3. **「东西放哪儿」映射表**（标准 2）
4. **自动获得的能力**：core 的 4 角色 + skills + 启动时注入的必载纪律 + hook 链路，一句话带过即可，不逐条罗列
5. **角色路由偏好**：推断出的 role_profile + 主力/按需/几乎不用三栏 + 一句「不符合实际可当场改」
6. **存量资料批次概览**（仅 B 路径）：按资料形态给批次与去向概览；**单份文件的安置与
   原件处置不在本页拍**——建树后的逐模块小闸（SKILL §5 步骤 4）深读后逐模块确认、当场执行
7. **CLAUDE.md / AGENTS.md 整合结果**（仅 B 路径且目标已有 CLAUDE.md 或 AGENTS.md）：见下方专节
8. **将要执行的动作清单**：建目录 → 落骨架 →（B 路径）写合并后的 CLAUDE.md / AGENTS.md →
   订阅 core → **git init + 首提交** →（探测到 `codex` 时）装 Codex 门 → 落盘验收，
   让用户知道确认后会发生什么
   —— **`git init` 是可勾选项，默认勾上**。没有 git，`.gitignore` 就是废的、可移植性检查会
   整个跳过、「同事 clone 接入好的项目」这条路径也不成立。目标已经是 git 仓时这一项不出现。
   —— **文件面取自脚本输出，逐字贴，不手写**：渲染本页之前先跑
   `project_scaffold.py … --print-plan`（命令与退出码语义见 SKILL §4），把它打出来的四格
   （`项目内·新建` / `项目内·改已有` / `项目外·改已有` / `已存在·本脚本不覆盖`）原样搬进本项。
   凭记忆复述过一次，漏掉的正是项目外那一格——它是整条链路上唯一一处「会改用户既有文件、
   却从没在确认页出现过」的写入。
   —— **第四格报的是「脚本不动的那些」，其中的 `CLAUDE.md` / `AGENTS.md` 逐项点名、由你写回**
   （框架自己的骨架文件在这一格里同样折叠成一行计数）：
   脚本对已存在的这两个文件一律跳过，合并稿在 SKILL §5 步骤 1.5 由你写盘，**脚本不知道
   这件事、也不会替你说**：预演只预演它自己那一步，**调用方在它跑完之后还要做什么，
   预演看不到、也无从断言**——合并稿是不是会被写回，只有调用方（这里是你）知道。
   所以贴完第四格之后要接一句：这两份的合并稿由我写回、原文去向在哪——展示标准走下方
   B 路径整合专节，本项只负责让它们在动作清单里有名字。
   —— **脚本输出必须包含下面这两行**（它们是「订阅 core」那一步的两处写入；哪一行没出现
   就是脚本坏了，不是本页可以省略的东西）：
   ①项目 `.claude/settings.json`（受保护资产，merge 两个键、你原有的键一个不动、先落备份到 `logs/`）；
   ②**用户级** `~/.claude/plugins/known_marketplaces.json`（补一条本市场的注册条目，同样 merge、
   同样先落备份）。②**不是项目级文件**，不在本页第 2/7 项那种「项目级三件事」的框架内，
   但它确实会改用户的既有文件——**动作清单是它唯一的露面机会，漏了它就等于没告诉用户**。
   **「本次不改」也要露面**：脚本对已是目标状态的那一行照样打出来并写明不改，本页照搬，
   不要因为「这次恰好不用改」就把它删掉。
   —— **③ 装 Codex 门这一步同样单独列一行**（探测到 `codex` 可执行文件时才有）。
   **这一行不在脚本输出里，要你自己加**：`--print-plan` 只预演骨架脚本
   （`project_scaffold.py`），它算不到 Codex 门那一步，输出里没有也不会有这一行。
   上一条的「逐字贴、不手写」**只管文件面那四格**——照着它把③一起省掉，就等于把
   这批 hook 信任唯一的事前授权点删了。它改
   **用户级** `config.toml`（本插件 hook 的信任 ＋ 本项目的 trust ＋ 本插件 `enabled` 改为 `false`）
   与项目 `.codex/`；**它会代你信任本插件的全部 hook，而受信 hook 脱离沙盒执行**
   （执行时逐条列出并报数），**且以后插件升级时，届时未受信的本插件 hook（变动过的与新增的）
   会在这台机器上任一接了 Codex 门的项目开 Codex 会话时自动补种信任、不再单问**——这半句必须
   一起写出来，经 launcher 装机时它是那次补种唯一的事前披露。**别在本页写死 hook 条数**——真实条数要门内前几步跑完才知道，
   而那几步本身有副作用；写死的数字会在 hook 增减时静默变成假话。措辞用「本插件的全部 hook」。
   这一行**不是可选的补充披露**：装 Codex 门这件事本身不再单问一层确认，本页因此成了
   这批 hook 信任**唯一的事前授权点**，只列①②会让授权面净变差。

### 第 8 项的能力边界

**本页是终端文本，机器看不见它渲染了什么。** `--print-plan` 把「凭记忆复述文件清单」换成
「跑一条命令并转述它的输出」——这是**降低失败概率，不是一道闸**：脚本跑没跑、输出贴没贴、
贴全了没有，都没有任何机器面看得到。真机上「模型到底贴没贴」仍然只能由人看着这一页判。

写出来是因为「没做」与「判过做不了」在读者眼里同形：这里是判过做不了，不是漏了。

## CLAUDE.md / AGENTS.md 整合结果（B 路径专节）

这是确认页里**改写用户既有文件**的几项中标准最严的一项——它改的是用户**自己写的正文**，
所以要逐段露出、逐条对照；另外两处（`.claude/settings.json` 与用户级市场注册表，见第 8 项）
改的是**机器可读的配置键**、且 merge 不动原有键，按动作清单点名即可，不走本节的展示标准。
**点名与展示是两件事**：这两个文件在第 8 项动作清单的第四格里有名字，但那一格只说
「骨架脚本不动它们」——改写它们的是你，所以展示标准仍然是下面这四条：

1. **合并稿按段落差异露出，不贴全文**（2026-08-11 定稿，取代早期「合并稿全文」要求，
   与 SKILL §3「只露含用户原文的段落」对齐）：**含用户原文的段落**逐段处理——原样保留的
   只列段名；被改写 / 被合并的给「原来是什么 → 现在是什么」对照；框架样板段（订阅声明 /
   快速入门 / 框架相关 / 委派子 agent / 两扇门的差异，每个项目一模一样）一行带过。用户想通读时随时给全文
2. **原文去向对照表**——原文每一段都要有一行，覆盖率 100%。格式与判据见 core 的
   `reference/claude-md-merge-guide.md` §第 3 步
3. **被覆盖项单独点名**——冲突默认框架优先，但每一条被框架口径取代的原文都要在正文里
   显式列出（不能只埋在对照表里），并说清「原来是什么 → 现在是什么 → 为什么」
4. **备份去向**——按 git 跟踪与干净状态判定的结果，明确告诉用户原文在哪、怎么回退

用户对被覆盖项有异议时：改的是**合并稿**，不是回头改框架骨架。改完按下方 §确认交互 的局部重渲染规则再确认。

## 确认交互

用 AskUserQuestion，三个选项：

- `按此执行`
- `我要调整` —— 用户用自然语句说改什么，改完**重渲染受影响的 section**、声明一句
  「其余未动」再确认（2026-08-11 拍板，取代「重新完整渲染」：旧拍板防的是口头描述代替
  渲染，局部重渲染不违背其动机）；改动牵连多个 section、或用户否定的是整体方向时，
  仍完整重渲染。不做增量口头描述
- `取消`

判据：用户补充事实或参数（改个名字、加个模块、换 role_profile）→ 合并后可直接执行；
用户否定方向或要求重来（「模块这么分不对」「换个思路」）→ 必须重新渲染 + 二次确认。
歧义时走二次确认，宁多一轮不少一轮。
