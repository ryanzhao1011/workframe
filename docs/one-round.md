# 一轮活怎么干

面向已经装好框架、准备动手改东西的人。这里只讲**一轮改动从开始到收口的顺序**，以及每一步该调什么。概念背景见 [核心概念](./concepts.md)；装机与接入见 [快速上手](./quickstart.md) 与 [初始化细节](./setup-guide.md)。

---

## 一句话

**改代码 → 更新受影响模块的文档 → 记一条账 → 跑一次收口检查 → 检查全绿再提交。**

收口检查就是 `module-close-check`。它不猜你想干什么，只回答一个问题：**这次改动还有哪些该落地的东西没落地**。

---

## 第 1 步 · 动手前：先确定改的是哪个模块

项目按功能链路切成基础模块 / 子模块（`projects/modules/<basic>/<sub>/`）。每个子模块的 `submodule.yaml` 里有 `code_paths`，声明「这个模块涉及哪些代码路径」。

动手前打开你要改的那个子模块的 `overview.md`，看清它的链路与影响面。**没有模块树的项目先建**：调 `module-init` 建基础模块与子模块，把 `code_paths` 填成本模块真实涉及的路径。

`code_paths` 是整套机制的地基——它空着，后面所有检查都无对象可查（`module-close-check` 会明确告诉你这一点，而不是给你一排绿勾）。

## 第 2 步 · 改代码

正常写。改完之后不要直接提交。

会话启动时框架会扫 git 改动，把受影响的子模块标成「文档过期」（stale）。你在会话里用 Edit / Write 改的文件也会实时标。这个标记是提醒，不是错误。

**它还会替你记着这轮活没收口**：只要清单上还挂着标记，下一次会话的第一句话里就会带一条待处理维护项，形如

```
[workframe] 待处理维护项 1 条（按 severity 排序）：
  - [info] PM-20260830-001 (close_check_due) — 2 个模块有 stale 标记未清：<模块>、<模块>——收口前跑 `workframe-module-close-check`（…）
```

所以隔了几天回来接着干、忘了上次改到哪，不用自己回想——它会告诉你还欠哪几个模块的收口。

## 第 3 步 · 更新模块文档

两件事：

1. **`current-state/`（代码现状）**：改动大到影响架构 / 接口 / 数据模型 / 文件角色时，调 `code-to-doc` 重新生成。它会同时写回子模块的 `submodule.yaml`（同步时间与基准 commit）并清掉 stale 标记。
2. **基准要一次刷全**。一次刷新要动五处，散在不同文件里——前三处装的是同一个「这份文档基于哪个 commit」，后两处装的是「这次同步与核对的情况」：

| 落点 | 位置 | 装什么 |
|---|---|---|
| `source_ref` | `current-state/*.md` 的 frontmatter | 基准 commit |
| `last_synced_ref` | `submodule.yaml` | 同上，须与 `source_ref` 同值 |
| 「基准 commit」括注 | 子模块 `overview.md` 的「最近同步」行 | 同上（自动渲染）|
| `last_synced_at` | `submodule.yaml` | 这次同步发生在什么时候 |
| `verifier` | `current-state/*.md` 的 frontmatter | 这次核对了哪几项、**不含**哪几项（不是 commit，随基准一起刷）|

**前三处漏刷任何一处，就等于同一个事实有了第二个来源**——`module-close-check` 的基准同值性检查会当场比对，不同值即报红。**后两处它不看**：各自只有一个落点，没有第二处装同一个值可比，不存在同值性这回事。漏刷它们不会红，代价是文档声称的核对范围停在上一份代码上。

**命中即刷**：只要你改的文件落在某个子模块的 `code_paths` 里，就刷那个模块的基准——哪怕这次只改了注释、行为零变化。刷的成本很低：`verifier` 那一句写你这次实际核对到什么程度就行，只改了注释就写「`git diff -w` 看过，非注释行改动为 0；没有重跑行为测试」这样一句。漏刷会让下一次对账失去参照。反过来，改动**不在**任何模块清单内时，不必刷。

**别只用肉眼找命中面**：`code_paths` 里既有具体文件，也有 `foo/**` 这类通配。只按文件名搜很容易漏掉被通配覆盖的模块。

## 第 4 步 · 记一条账

**这一步默认就是开着的，装完机不用配。** 脚手架已经在 `.workframe-config.json` 里写好了账本位置与必含字段，也已经建好 `projects/dev-log.md` 并写下第一条：

```json
{
  "close_check": {
    "ledger": "projects/dev-log.md",
    "required_fields": ["模块", "背景与根因", "改动", "连带", "验证", "提交", "遗留"]
  }
}
```

想换个位置、或增删必含字段，直接改这个键。

账本条目的格式（下面这条**照着抄就是齐的**——七个字段与上面那份默认清单一一对应，少一个就报红）：

```markdown
## 2026-08-30 · 一句话工作线标题

- **模块**：<basic>/<sub>（涉及的都列）
- **背景与根因**：为什么要动它
- **改动**：逐文件写清改了什么
- **连带**：受影响的连带项处理情况；评估后决定不改的附一句理由
- **验证**：怎么验的、验了哪几项、**不含**哪几项
- **提交**：commit hash
- **遗留**：→ 看板任务 id，或「无」
```

一级项是 `## YYYY-MM-DD · 标题`，**最新的一条放在最上面**（检查只看文件里的第一条）；其下每个必含字段写成 `- **字段名**：内容`（冒号全角半角都认）。字段头存在即可，内容允许写在下级子项里。改了 `required_fields` 就照改后的清单写，这份示例只是默认清单的样子。

不想记账的项目，把那个键改成空壳 `"close_check": {}`，账本检查随即整项跳过，不影响其余八项。**是改成空壳，不是删键**——脚手架写配置时「本地缺失才写」，删掉的键下次重跑会被原样写回；空壳则不会被覆盖。

**空壳只关账本这一项**，不连带关掉别的。第 8 项「YAML 可解析性」要单独关，写显式声明：

```json
"close_check": { "yaml_parse": false }
```

**什么时候会想关它**：这一项要用真 YAML 解析器（PyYAML）读一遍模块文档，而 PyYAML 不是本框架的硬性前置依赖。本机没装时它**报红而不是报绿**——「这一项没跑」和「这一项通过」不是一回事，静默报绿等于替你声称验过。两条出路二选一：`pip install pyyaml`，或者按上面写一句显式声明把它关掉。**关掉是一次留了记录的决定，缺库静默跳过不是**，所以框架不替你做后者。

该声明同时作用于 `workframe-doctor` 的 `yaml_parse` 项（它查的是 `board.yaml` / issues / proposals，与收口检查查的文件不重叠）——同一件事的两半，一个声明一起关。

**顺序有讲究**：先提交主体改动拿到 hash，再写账本条目（把那个 hash 填进去），账本本身随后单独提交。反过来的话，账本里只能写「本次提交」这种事后没法定位的指代。

## 第 5 步 · 跑收口检查

```bash
workframe-module-close-check
```

命令不在 PATH 上时直接跑脚本：

```bash
python "$(cat .workframe/state/plugin-root.txt)/scripts/module_close_check.py"
```

**正确时点**：模块文档与账本都写完之后、外层仓收口提交之前。代码仓本身应该已经提交——基准 hash 只有提交后才存在。其余收尾动作（看板状态流转、为用过的 skill 记事件）也在它**之前**走完：第 9 项看的正是这些痕迹，先跑再补会先红一次。

**不用自己记着这一步**：第 2 步那条提醒就是来叫你跑它的，它自己会在会话开头出现（`/core:audit` 也能随时看全部待处理项）。

除它自己的计数日志外（第 9 项同时读这份日志算升级计数），它不改动任何被检对象。任一 error 则 exit 1。

九项检查各自在查什么：

| # | 检查 | 红了通常意味着 |
|---|---|---|
| 1 | 过期标记已清 | 改了代码但对应模块文档没更新 |
| 2 | `code_paths` 形态与指向 | 清单里的文件被改名 / 删了，或通配已经指不到任何东西 |
| 3 | 基准引用同值 | 第 3 步的几个落点漏刷了其中一处 |
| 4 | 命中模块已刷新 | 基准之后又动过这个模块的代码，但基准没跟上 |
| 5 | 代码仓提交状态 | 工作树还脏 / 领先远端（中性提示，不是错） |
| 6 | 代码索引覆盖率 | `code-map` 声明覆盖的文件集与 `code_paths` 对不齐 |
| 7 | 账本条目字段 | 这轮工作没记账，或条目缺必含字段 |
| 8 | YAML 可解析性 | 模块文档不是合法 YAML（不可见控制字符 / 标量里的裸引号 / 占位符没渲染），或本机没有 PyYAML 因而这一项**没跑** |
| 9 | 纪律产物痕迹（warn 档） | 昨天 00:00 以来改过模块代码，却没记账（与第 7 项同源），或命中模块的看板任务都没在今天 / 昨天更新；窗口内零 `skill_used` 只作提示 |

第 8 项只证明**文件是合法 YAML**，不证明「框架各处的正则读数与真解析器一致」——重复键这类「两边都读得出、取值却不同」的形态它看不见。它红的时候，前 7 项对那份文件的读数也不可信：那几项走正则，可能读到脏值，也可能读成「字段不存在」。

第 9 项是 **warn 档，不阻断收口**。它只在「昨天 00:00 以来有子模块的 `code_paths` 被改过」时才判；绿是**项目级**痕迹——别的会话或子 agent 留下的记录同样让它绿，所以多会话、高频的项目里它分辨力低。每次运行它往状态目录的 `discipline-trace-log.jsonl` 追加一行，并现算连续合格收口的次数：满 10 次、分布在 ≥7 个本地日、且其间每一次红都确认过，才**建议**把它升为 error（不会自动升）。要确认一次红，用输出里「本次运行指纹」那一行给的命令：`workframe-discipline-mark --fingerprint <指纹> --verdict missed|false-positive --by qa|user|self`——「确实漏做」谁都能标，「闸判错」只收 qa / user。收尾步骤没走完就跑出的红不算闸判错，走完重跑即可。

**红灯文案自带修法**——它会直接告诉你缺什么、该补成什么格式，不需要回来查文档。

## 第 6 步 · 全绿再提交

`error 0` 才算收干净。`warn` 是提示（例如工作树还有无关的 WIP、本地领先远端几个提交），不阻断。

## 常见情况

**「全是绿勾，但我一个模块都还没建」**——不会出现这种误导了。模块目录在但没有任何子模块时，命令会合并成一条提示并说明怎么让检查真正生效，而不是给你一排绿勾。

**「这几天没干活，也要被判没记账？」**——不会。账本条目过老时，命令会先看那天之后根仓有没有提交、工作树是否干净；两者皆无就只作提示。判断不了（不是 git 仓 / git 不可用）时才回落到无条件报红，并在文案里说明这是降级。

**「还没开始记账就被报红？」**——同上，没有账本文件、或账本里还没有任何条目时，同样按「这段时间有没有活」判定。

**「账本模板里的示例条目被当成真条目了」**——HTML 注释块（`<!-- ... -->`）内的内容不参与匹配。

**「那条收口提醒怎么才不再出现」**——正常路径就是把活收完：更新模块文档时调 `code-to-doc`，它会顺手清掉对应模块的过期标记；清单空了，提醒自然不再出现。只手工刷了基准、没跑 `code-to-doc` 的，标记要自己清（**别手改 `stale-modules.yaml`**，那份文件有 hook 并发写入）：

```bash
python "$(cat .workframe/state/plugin-root.txt)/scripts/check-stale-modules.py" \
    clear-stale "<basic>/<sub>" --reason "<一句话处置理由>"
```

**「我这会儿不想收口，能把它关掉吗」**——能，`/core:maintenance-review --dismiss <PM-ID>`。关掉的含义是「**这批过期标记我认了，先不处理**」，所以之后你再改这些模块的代码、被重新标上过期，它还会再提醒一次——那是新的一轮活，不是同一条提醒复活。

一句实话：关掉的效力只有一个保留期（当前 7 天，写死在代码里、不是配置项）。那条关闭记录到期被清理后，标记要是还挂着，它会再问你一次。这是有意的——**没收口的活不会因为你关过一次提醒就消失**。真想让它彻底安静，只有把活收完这一条路。
